# Repository Instructions

This repository is Justin's cross-platform AI skills collection. Follow these instructions whenever adding or modifying a skill.

## Repository Structure

Use a monorepo structure:

```text
skills/                  # Source directory for each skill
packages/                # npm packages for skill installers
scripts/                 # Build, sync, and release helper scripts
```

The root `package.json` must remain `private: true`. It is only for workspace management and must not be published to npm.

Each publishable skill uses an independent npm package:

```text
skills/<skill-name>/SKILL.md
skills/<skill-name>/README.md
skills/<skill-name>/agents/openai.yaml
packages/<skill-name>-skill/package.json
packages/<skill-name>-skill/bin/install.js
packages/<skill-name>-skill/skills/<skill-name>/   # Generated by build; do not edit by hand
packages/<skill-name>-skill/README.md              # Generated by build; do not edit by hand
```

`skills/<skill-name>` is the single source of truth for the skill content. `packages/<skill-name>-skill/skills/<skill-name>` and `packages/<skill-name>-skill/README.md` must be generated by `scripts/sync-skill-package.js` or an equivalent sync script. Do not manually copy skill files into package directories.

## Skill Content Standards

Every skill must include:

- `SKILL.md`
- `README.md`
- `agents/openai.yaml`

`SKILL.md` requirements:

- Frontmatter must include `name` and `description`.
- `description` must be in English and clearly state when the skill should trigger.
- The body must begin with an English slogan immediately after the frontmatter.
- The main body should be written in English for a global audience.
- If a skill can output Chinese or English, default to the user's current conversation language. Only force a language when the user explicitly passes an argument such as `--lang zh` or `--lang en`.
- Keep localized output examples descriptive, not literal. Do not put full non-English Markdown template blocks in `SKILL.md`; explain in English that headings and labels should be localized instead.
- Do not add CHANGELOG, INSTALLATION_GUIDE, or similar extra docs inside a skill directory unless the user explicitly asks for them.

`README.md` requirements:

- Keep this file in `skills/<skill-name>/README.md`; do not hand-edit package-local README files.
- The sync script must copy it to `packages/<skill-name>-skill/README.md` before pack or publish so npm can render the package README.
- Keep it concise and user-facing: install command, supported tools, invocation examples, language or option rules, and what the skill produces.

`agents/openai.yaml` requirements:

- Include at least `interface.display_name`, `interface.short_description`, and `interface.default_prompt`.
- `default_prompt` must explicitly include `$<skill-name>`.
- UI-facing text should be in English.

## npm Package Standards

Each skill maps to one publishable npm package:

```text
@justinforfun/<skill-name>-skill
```

Each package must include:

- `"type": "module"`
- A `"bin"` field pointing to `./bin/install.js`
- A `"files"` allowlist containing only release artifacts
- `"publishConfig": { "access": "public" }`
- A `"scripts.build"` command that syncs root `skills/<skill-name>` into the package
- A `"scripts.prepack"` command that runs build before pack or publish
- A `"scripts.check"` command that at least runs `node --check bin/install.js`

Default installer stack:

- Node.js ESM
- `inquirer`
- `chalk`
- `ora`

Do not make users enter installation paths in the default flow. Prefer the mainstream default directories for each target AI tool. Only offer custom paths for uncertain tools or advanced modes.

## Installer Interaction Standards

Installers should provide a clean interactive UI:

- List supported AI tools.
- Support arrow-key movement, spacebar multi-select, and Enter confirmation.
- When the same skill already exists, offer:
  - `Backup then overwrite` as the recommended default
  - `Overwrite`
  - `Skip`

Initial target tool conventions:

- Codex: install to `~/.agents/skills/<skill-name>`
- Codex CLI: install to `${CODEX_HOME:-~/.codex}/skills/<skill-name>`
- Claude Code: install to `~/.claude/skills/<skill-name>`; if the skill needs a real slash command, also generate `~/.claude/commands/<skill-name>.md`

Do not promise native slash-command support for every tool. README files and installer output must explain the real invocation method for each supported tool.

## README Standards

The repository root must maintain bilingual README files:

- `README.md`: default English version
- `README.zh-CN.md`: Chinese version

Both README files must include language switch links at the top:

```markdown
[English](./README.md) | [中文](./README.zh-CN.md)
```

When adding, removing, or changing a skill, update both README files. At minimum, include:

- Skill name
- What the skill does
- Installation command
- Invocation method for each supported tool
- Language rules or important arguments
- Development, build, check, and publish commands when they change

Never update only one language version.

## Makefile Standards

The root `Makefile` should wrap common commands so users do not need to remember long npm commands.

Keep at least:

```text
make install
make build
make check
make pack
make publish
make run
make version
make clean
```

This repository has no default publish package. Commands that target a specific npm package must require a skill name via `SKILL` or a positional argument:

```bash
make build SKILL=<skill-name>
make pack SKILL=<skill-name>
make run SKILL=<skill-name>
make version SKILL=<skill-name> BUMP=patch
make publish SKILL=<skill-name>
make publish <skill-name>
```

The Makefile derives the npm package as `@justinforfun/<skill-name>-skill`.

`make publish <skill-name>` must automatically run checks, dry-run pack, bump the package version, and publish. The default bump is `patch`; use `BUMP=minor` or `BUMP=major` when needed. Use `make version <skill-name> BUMP=patch|minor|major` only when bumping without publishing.

## Release Flow

Before publishing, run at least:

```bash
make check
make pack SKILL=<skill-name>
```

`make publish SKILL=<skill-name>` must run checks, a dry-run pack, `npm version`, and then `npm publish`.

```bash
make publish SKILL=<skill-name>
```

For first-time publishing or expired npm credentials:

```bash
npm login
npm whoami
make publish SKILL=<skill-name>
```

If npm requires two-factor authentication for publish, pass the one-time password through `OTP`:

```bash
make publish <skill-name> OTP=123456
```

`make publish` does not log in to npm automatically.

## File Hygiene

- `.DS_Store`, `node_modules/`, and `*.tgz` must be ignored by `.gitignore`.
- Do not hard-code `.DS_Store` deletion in sync scripts. Handle it through `.gitignore` and workspace cleanup.
- Do not commit generated tarballs.
- It is acceptable to commit the package-local synced `skills/<skill-name>` directory because it is part of the npm package release surface. However, edits must be made in root `skills/<skill-name>` first, then synced.

## Existing redo Skill Contract

`redo`'s core philosophy:

> Every mature system is a fossil record of the constraints it survived.

`redo` is not a feature tour. It reconstructs the evolution of a technology through:

- Stage constraints
- Candidate options
- Option costs
- Why the final choice won
- Key trade-offs
- Technical debt introduced
- Later debt repayment
- Still-unresolved pain points
- A final causal chain

For real technologies, if the user has not forbidden browsing and the environment allows it, verify with official documentation, release notes, RFCs, papers, design docs, or authoritative engineering blogs first. If online research is unavailable, explicitly say the analysis was not freshly verified online.
